## 兑换状态与持久化

现有实验中的同一 requestId 可跨刷新重放而不重复扣款，页面内 Map 能处理同页重登。正式版本需要**服务器持久化的兑换意图和收据**，刷新或换设备后仍能发现未确认的结果。

本草案选择每成员、每商品同时最多一个未确认意图，避免用户因响应丢失再次创建一笔。成员确认旧结果后才能明确发起新兑换。此约束属于待真实 TEST 和业务审核的规则。

拟增加独立订单表，字段包含不可猜测 order_id、服务端 member_id、商品 ID、可信价格快照/币种/规则版本、请求唯一键、状态、创建/过期/提交/确认时间、台账外键和脱敏错误码。金额使用有界整数和 CHECK；所有者/删除权限与普通运行角色分离。正式 SQL 先适配真实 TEST 的 ID、外键和迁移历史。

状态为 prepared → committed 或 failed/cancelled。已提交的账务不可通过重试或取消删除。confirmed 是收据确认标记，与财务状态分列。唯一约束包括成员/请求键、台账业务键和成员/商品的未确认意图。过期清理先锁定行，不能把已提交订单改成取消。

## 建议 API 流程

这些为待实现的逻辑契约，最终 Netlify 路由由明确的 Function 分派处理。

1. 登录状态恢复后先读取本人的未确认意图与收据。GET 仅读取，private/no-store。服务端从有效会话获取 member ID，忽略客户端账号和 memberId，最小字段分页返回，错误与空列表分开。
2. 创建意图时提交商品 ID 与幂等请求键。服务端核验目录、服务端价格和权限。在事务内查询或创建本人的未确认意图，唯一约束解决设备并发。创建响应丢失时，下一次查询可找回该意图。
3. 明确提交该意图时核对会话、CSRF/Origin，按固定顺序锁订单和余额。若已 committed，返回既有收据；若状态或价格有效期需要再次确认，返回明确冲突。额度和商品库存规则由服务器验证。
4. 成功扣款、商品履约记录、唯一台账、余额更新和 committed 收据在同一事务提交。外部履约若未来出现，使用可幂等 outbox，先审批可靠补偿模型。事务失败则全部回滚。
5. 页面只在读取到 committed 收据后显示成功。网络中断保留“待核验”，刷新及换设备会查询同一成员的未确认订单。不得自动生成新编号重试未知结果。
6. 用户看到结果并主动确认后 POST 确认收据。确认响应丢失可重复提交。另一设备的老订单 ID 仍可查询，确认不会撤销或隐藏不可变流水。发起下一笔需明确的“再次兑换”操作。

提交、取消与确认均验证成员主体、状态版本、CSRF 和同源。跨账号查询/提交订单使用统一拒绝行为，避免泄漏订单是否存在。GET 不进行确认或账务变更。余额失败显示不可用；旧余额不能授权兑换。

## 必须执行的故障与并发测试

| 场景 | 预期 |
| --- | --- |
| 创建响应丢失，刷新/换设备 | 未确认列表找回同一意图，余额未扣 |
| 提交成功但响应丢失，刷新/换设备 | 找回同一 committed 收据，台账/余额只改变一次 |
| 同账号双标签、双设备同时创建/提交 | 唯一约束和事务返回同一未确认订单；无负余额、超卖或重复台账 |
| 同商品连续合法兑换 | 前一收据确认后明确新意图，两次扣款各有独立收据 |
| 客户端篡改身份、金额、商品或订单 | 服务器主体与目录决定，跨成员拒绝，订单与商品不匹配返回冲突 |
| 目录下架、规则改价、意图过期 | 已提交收据仍可恢复；未提交意图按明确政策取消或重新确认 |
| 扣款中断/约束失败/死锁重试 | 事务原子回滚，同一请求可安全重试，固定锁顺序及受限重试 |
| 注销、会话过期、锁定、停用 | 所有写入拒绝。重新有效登录后仍可读取本人的历史收据 |
| 确认响应丢失/两设备确认 | 确认幂等，不重复扣款，不改变财务结果 |
| 断网时已有本机草稿 | 保留草稿并显示待核验；重连先恢复会话和服务器订单 |

第 1 批恢复可信登录/资料/改密，第 2 批恢复带主体的内容，第 3 批在本设计通过后恢复积分，第 4 批处理组队、管理、赞助和公开榜单。 [分批恢复依赖](../b2-a-5/RESTORE_SEQUENCE.md)

回滚先关闭新写入口，保留订单和不可变流水供核账，撤销新运行权限。只读历史与用户草稿继续可用。正式表迁移的回退由 TEST 的备份恢复演练证明后另行审批。
